## 2. 架构评估

### 2.1 总体设计:🟢 健康

```
SshClient ─► SshSession ─► SshTransport(接口)
                              ▲
                              └── ChannelTransport(生产) / FakeTransport(测试)
```

- **依赖方向正确**:UI → SshClient → SshSession → SshTransport(可注入接口);数据层独立,无反向依赖。
- **职责清晰**:`terminal/` 负责 IME 链路与渲染,`ssh/` 负责传输,`data/` 负责凭据持久化,`ui/` 负责 Compose 装配。
- **关键解耦点做对**:
  - `SshTransport` 4 方法窄接口,使单测不必 mock SSHJ 的 700 行 `Channel`。
  - `Auth` sealed class + `SshAuthProvider` strategy,新增认证方式编译期强制覆盖。
  - `TerminalEndpoint` SAM 接口,`MockEchoSession` 与 `SshSession` 互换,UI 零改动。

### 2.2 数据流:🟢 严谨

- `refreshSignal = Channel<Unit>(CONFLATED)` 合并多包为单次 invalidate,不会因 SSH 高吞吐触发重绘风暴(`TerminalPane.kt:71`)。
- `writeExecutor = Executors.newSingleThreadExecutor` 串行化 outbound,避免多键同时到达时字节交错(`SshSession.kt:55`)。

### 2.3 IME 双链路分离:🟢 教科书级别

`TerminalView.onKeyDown` 的路由决策表与文档严格一致,可打印字符放行给 IME、Ctrl/Alt 转义由 View 吞掉、组合中 DEL 走 IME。`KeyMapper.KeyResolution` 的 `Send / Swallow / Ignore` 三态语义清楚,且 `KeyEventRoutingTest` 把每条规则都钉死。

## 3. 代码质量(逐文件)

### 3.1 `MainActivity.kt` 🟡

- **问题**:把 `CrashHandler`、`HanTermApplication`、`MainActivity` 三个无关类塞进同一个文件(84 行,单文件 3 个顶级类)。`CrashHandler` 是通用基础设施,应放 `data/diag/` 或 `util/` 包,目前与 `MainActivity` 同名空间且不带子包,违反"一个文件一个公开类型"的常规 Kotlin 习惯。
- **建议**:拆为 `diag/CrashHandler.kt` + `HanTermApplication.kt` + `MainActivity.kt`。
- **小问题**:`appendText` 不分大小,改 `Charsets.UTF_8` 显式声明会更稳(目前是平台默认)。

### 3.2 `SshClient.kt` 🟢

- 实现紧凑,`runCatching` + `withContext(Dispatchers.IO)` 模式标准。
- PTY 模式注释里 `ECHO + ECHOE` 的设计解释清晰。
- **小问题**:`hostKeyVerifier = PromiscuousVerifier()` 默认值是无脑接受任何主机指纹。生产环境必须改进(`SshConfig.kt` 与 `SshClient.kt` 注释也提到 Sprint 3 加 TOFU),但 v1.0 MITM 风险需要更醒目的 README 警告,目前仅有 kdoc。

### 3.3 `SshSession.kt` 🟢

- `AtomicBoolean` + `writeExecutor` 的幂等关闭模式正确。
- `awaitWriteQueueDrained` 仅供测试用,正确标 `internal` 并注释约束。
- **建议**:`readInto` 内 `currentCoroutineContext().isActive` 每次循环都读一次,可优化为先取一次 `val active = ...` 然后比较,但实际开销可忽略。
- **小问题**:`readBytes()` 在 IO 阻塞读上没有显式超时,完全依赖 `currentCoroutineContext()` 取消传递。如果 SSH 通道挂死(socket 未关),`readInto` 永远不返回。Sprint 2.5 建议加一个定期"看门狗"(例如 30 分钟 idle 主动重连或上报)。

### 3.4 `SshConfig.kt` 🟡

- `READ_TIMEOUT_MS: Long = TimeUnit.SECONDS.toMillis(0)` —— 注释说"在 IO loop 上读超时,触发干净 EOF 中断",但 `SshSession.readInto` 实际上**没有用这个值**。这是个死代码,要么用上,要么删掉。
- `KEX_TIMEOUT_MS` 同理,`SshClient.connect` 里只设了 `setConnectTimeout`,kex 用的 `setTimeout` 没显式调用。这两个常量目前是文档级而非真实配置。

### 3.5 `ChannelTransport.kt` 🟢

- `flush()` 必加(注释里也强调 SSHJ 默认缓冲)。
- `closeQuietly(channel as java.io.Closeable)` 注释解释了为什么 cast。
- **小问题**:`READ_BUFFER_BYTES = 8 KiB` 是从 SSHJ 内部抄的魔法数,没解释来源;建议加一个测试或 kdoc 说明。

### 3.6 `BouncyCastleBootstrap.kt` 🟢

- `synchronized(lock)` + `runCatching` 兜底,适合在 Robolectric 沙箱里也安全。
- 解释 BC 版本不匹配的部分很到位。

### 3.7 `auth/Auth.kt` 🟢

- sealed class 用法纯正,`when` 强制穷尽。

### 3.8 `auth/PasswordAuthProvider.kt` 🟡

- **安全问题**:虽然日志只打 SHA-256 前 16 位 + firstByte,但 SHA-256 截断仍可能用于离线爆破短弱口令。生产环境应直接关掉 `Log.i` 这一行,或仅在 debug build 输出(用 `BuildConfig.DEBUG` 守卫,目前 `build.gradle.kts` 没启用 `buildConfig` 特性)。
- **安全债**:`auth.password` 是 `String`,JVM 上无法原地清零;`PasswordAuthProvider` 注释自己也承认了。建议把 `Auth.PasswordAuth` 改成持有 `CharArray` + 配套的 `zeroOut()` 调用,而不是 `String`。

### 3.9 `auth/PublicKeyAuthProvider.kt` 🟢

- `loadKeyProvider` 的 format 自动检测优雅,且不加载 key material 出 JVM。
- 加密私钥(passphrase 保护)显式声明"v1.0 不支持",不会静默退化。
- 同样,`SshConfig.kt` 注释里说明"v1.0 不通过 Keystore 解密私钥,文件以明文存于 `filesDir/keys/`"——**这是一个明显的安全妥协**:`filesDir` 在非 root 设备上有沙箱保护,但 root / adb backup 攻击面上是裸的。`AndroidManifest` 已 `allowBackup="false"` 是个加分项。建议至少在 Sprint 2.5 给私钥本身也过一遍 Keystore(AES-GCM 加密 PEM 文件),与密码同等保护。

### 3.10 `terminal/TerminalView.kt` 🟢(整体)🟡(细节)

- 这是整个项目最复杂的文件(315 行),集成了:
  1. `TerminalViewClient` 的 stub 实现
  2. `TerminalEmulator` 的构造 + 内部状态访问(`mEmulator` 反射赋值)
  3. `TerminalOutput` 的 transcript 回调
  4. `onCreateInputConnection` 输入约定
  5. `onKeyDown` 路由决策
  6. PTY resize 监听
- **值得肯定**:每个 hack(直接读写 Termux 内部字段)都附了 SSH_ANDROID_PITFALL 注释解释为什么,这是好习惯。
- **风险**:
  1. `termuxView.mEmulator = e` 走的是 Termux 包的 `internal` 字段(`@SuppressWarnings("restOfVisibility")` 之类),Termux 一旦升 v0.119+ 改名就会编译失败,需要锁定 patch 版本,目前已经锁 v0.118。
  2. `termuxView.mRenderer` 同样在 `reportPtyResize` 访问,需要持续对齐 Termux 内部 API。
  3. `try { ... } catch (t: Throwable) { writeCrashLog("TerminalEmulator construction failed", t); throw t }` 这段是无操作代码——catch 后又 throw,等于把 catch 块变成纯日志。直接移除 catch 即可。
  4. `lastResizeCols/Rows` 防抖逻辑正确,但 `onAttachedToWindow` 注释说"requestLayout + invalidate"——这里没有调用 `updateSize()`,与 `reportPtyResize` 注释"updateSize() 是 no-op without mTermSession"形成轻微矛盾,需要在 Sprint 3 复测一遍真机。
- **`writeCrashLog` 与 `CrashHandler` 重复**:两处独立实现,前者写到 `crash.log`,后者也是。建议统一入口。

### 3.11 `terminal/TerminalInputConnection.kt` 🟢

- `userInImeContext` 这个"组合意图锁存"是真正解决 Gboard P0 竞态的优雅方案,值得在更显眼的位置(README)描述。
- **小问题**:
  - `setComposingRegion` / `setSelection` 直接 `super` 不变,这俩方法 Kotlin 不需要重写,删掉 override 更清爽。
  - `@Volatile` 在单线程(UI 线程)访问下其实是过度防御,可保留(便宜)但应注释说明意图。
  - `composingBuffer: StringBuilder` 实际上**从未被读取**——`setComposingText` 清空+写,但没消费者。建议删除死代码,或加 `getComposingText()` 供 View 端 hint(目前 hint 是直接传 text,不读 buffer)。

### 3.12 `terminal/KeyMapper.kt` 🟢

- 清晰映射表,F1-F12 全覆盖。
- **小问题**:
  - `isImeLanguageSwitch` 注释与 `KEYCODE_LANGUAGE_SWITCH` 在 `resolve()` 里分别判断,后者是 keyCode 比较,不依赖事件 modifier,因此放最前。这段逻辑顺序正确但读起来费劲,可重排为单一 `swallowKeys(keyCode, event)` 辅助函数。
  - `toAnsiSequence` 注释说"backwards-compatible",但全仓只有 `TerminalInputConnection.sendKeyEvent` 在用,而后者也只关心 `null` vs `bytes`——可以删掉这个 wrapper,直接叫 `resolve()`。

### 3.13 `terminal/MockEchoSession.kt` 🟡

- `writtenBytes: MutableList<Byte>` 用 `Byte.toList()` 转 `List<Byte>`,测试时拼接再 `flattenToByteArray`。简单 OK,但在字节量大的场景效率不佳(目前不构成问题)。
- **建议**:`writtenBytes` 类型用 `ArrayDeque<ByteArray>` 更直白,`bytesWritten()` 用一次拷贝返回 `ByteArray`。

### 3.14 `data/crypto/KeyStoreManager.kt` 🟢

- AES-256-GCM 12 字节 IV 拼接的 payload 格式标准,`GCM_TAG_BITS = 128` 正确。
- `KeyGenParameterSpec` 锁定了 `PURPOSE_ENCRYPT|DECRYPT + BLOCK_MODE_GCM + NoPadding + 256-bit`,完全够用。
- **小问题**:
  - 缺 `setUserAuthenticationRequired(true)` 的可选升级路径,注释里提过但未实现——`KeyStoreManager` 留个 `requireUserAuth: Boolean` 参数比较自然。
  - `deleteKey()` 当前没有任何调用方(Sprint 2.5 "forget this device" 才用),保留即可但可标 `@VisibleForTesting` 或注明"暂未挂入 UI"。

### 3.15 `data/prefs/AppPreferences.kt` 🟢

- `hasUsableCredentials` 用 Plan C 的 encrypted slot 判断,而不是 `password`(legacy 字段),这点与 ConfigScreen 对齐。
- **小问题**:
  - 每次属性 `get` 都新建一个 `prefs.edit()`,没有缓存 editor——`SharedPreferences` 内部有缓存,可接受。
  - `setEncryptedPassword(ByteArray(0))` 的"空口令哨兵"语义,依赖调用方主动写空数组;`getEncryptedPassword` 把空转 null。逻辑闭环,但应加一条测试覆盖"先 set 非空再 set 空,get 返回 null"——目前测试里只有两种独立场景。

### 3.16 `ui/HanTermApp.kt` 🟡

- **可测试性差**:`runConnect` / `resolveAuth` 是 top-level private 函数,UI 状态机 `ConnectionState` 是顶层 sealed class。Composable 函数 `HanTermApp` 里有 70+ 行耦合到 `Context` / `prefs` / `sshClient`,没法独立 unit test。
- **建议**:抽 `class SshTermViewModel(...)` 把连接状态机、凭据解析、连接逻辑都搬过去,Composable 只负责渲染。Sprint 2.5 路线图可以加。
- **小问题**:
  - `if (isBusy) return@Button`——Button 的 onClick 接收 `() -> Unit`,正确。
  - Disconnect 流程:先 `activeSession = null` 再 `sshClient.disconnect()`,注释解释了"先 null 触发 IO 协程 cancel,再断父 client",但实际 LaunchedEffect 依赖的是 `sshSession` 状态变化——这里的顺序正确,但如果未来改成 ViewModel 持有,要小心避免 race。

### 3.17 `ui/ConfigScreen.kt` 🟡

- 382 行,Composable + 一堆 helper 堆一起,职责过多:
  1. 表单 UI
  2. SAF 私钥导入
  3. 密码指纹计算与日志
  4. 崩溃日志展示
  5. 持久化写入
  6. 文件名 sanitize
- **建议**:
  - 拆出 `PrivateKeyImporter.kt`(SAF + 文件拷贝 + sanitize)
  - 拆出 `CrashLogCard.kt`(展示 + 复制 + dismiss)
  - Composable 主体降到 ~150 行
- **安全问题**:
  - `appendDebugLog(context, "save host=$host port=$port user=$username password=$fp ...")` —— 把 host/port/username 写入 app-private `debug.log`,这个文件路径注释说"adb pull 可读",**意味着 debug APK 一旦装到设备,任何人有 USB 调试权就能拿到主机地址和用户名清单**。Sprint 2.5 应默认关闭 debug 日志(用 `BuildConfig.DEBUG` 守卫,目前没启用 buildConfig 特性),或加 UI 开关。
  - `passwordFingerprint` 函数本身合理,但被广泛用于写日志,加剧了上面那个问题。
- **小问题**:
  - `LaunchedEffect(statusMessage) { delay(2000); statusMessage = null }` 协程在 `statusMessage` 变化时会重启,这意味着连续点 Save 两次会在第二次后恰好清空第一次的"Saved"——这是个小 UX 瑕疵,可改成 `LaunchedEffect(statusMessage, key=...)` 不依赖值的重启,或者用 SnackbarHost。
  - `OutlinedTextField(value = port, onValueChange = { port = it.filter(Char::isDigit).take(5) })`——`.take(5)` 限制最大字符数 5,但合法端口最多 5 位数字,边界 OK;但如果用户输入超过 5 位,他会感觉字段"卡住"了,应加 `supportingText = { Text("1-65535") }`。
  - `importError` 用 `Color.Red` 硬编码,违反 Material 3 主题——应 `MaterialTheme.colorScheme.error`。
  - `lastCrash` 内的 crash trace 用 `fontSize = 9.sp`——9sp 接近 WCAG 最低可读性,平板上长 stack trace 会变成密麻小字,可用 `Text(... overflow = TextOverflow.Scroll)` + `Modifier.verticalScroll()` 改善。

### 3.18 `ui/TerminalPane.kt` 🟡

- 84 行,逻辑核心是 `LaunchedEffect(sshSession, viewHolder.view)`。
- **生命周期问题**:`viewHolder.view` 写入在 `AndroidView.factory` 闭包里,但 LaunchedEffect 用它当 key。`AndroidView` 的 `update` 也会重置 endpoint + listener,这是有意的(每次 endpoint 变化重新绑定)。
- **潜在 bug**:`factory` 与 `update` 都会设置 `composingHintListener` 与 `bindEndpoint`,但 `view.setPtyResizeListener` 只在 `LaunchedEffect` 内部设置(第 67 行)。如果 endpoint 变化(连上 → 断开)但 view 不变,`LaunchedEffect` 的 key 没变,**不会重启**——`ptyResizeListener` 仍然挂在 view 上指向**旧** session 的 lambda(因为 lambda 闭包变量 `session` 仍然有效)。Disconnect 时 `setPtyResizeListener(null)` 是在第 92 行(L IO loop 结束后)清理,但仅当 LaunchedEffect 重新进入时——一旦 key 不变,清理不发生。
  - 这是一个**潜在的 listener 泄漏**。建议把 `ptyResizeListener` 的清理移到 `DisposableEffect` 里,或者让 listener 本身接受 nullable session 并在 null 时短路。
- **小问题**:`Channel<Unit>(CONFLATED)` 注释和实现清晰;`launch(Dispatchers.Main) { for (signal in refreshSignal) ... }` 协程在 effect 结束时会自动取消(channel close 触发 for 循环结束)。

### 3.19 `theme/Theme.kt` / `Color.kt` / `Type.kt` 🟡

- 颜色统一在 `Color.kt` 定义(`WarpBackground/Surface/Accent/...`),OK。
- **不完整**:
  - 没有 `lightColorScheme` 适配浅色主题——`SshTermTheme` 永远 `darkColorScheme`。终端用户群(开发者)通常深色偏好,可以接受,但应在 README 注明"目前仅深色"。
  - 缺 `MaterialTheme.colorScheme.secondary / tertiary / error` 等定义,主题覆盖度仅 5 个 token,后续加按钮 / chip 时会缺色。
  - `AppTypography` 只设了 `bodyLarge` 16sp monospace,其他 token 走 Material 3 默认——但 Compose 默认字体是 sans,与终端等宽需求不符,可能造成混合字体排版。
- **`styles.xml`**:`android:fontFamily="sans"` 与 Compose `Monospace` 不一致,Compose 组件覆盖了 View 层,但 crash log 文本显示走 TextView(AndroidView 子树中),字体可能继承系统 sans。

### 3.20 `AndroidManifest.xml` 🟢

- 权限声明带详细注释,INTERNET + ACCESS_NETWORK_STATE 正确。
- `android:allowBackup="false"` 防 `adb backup` 迁移数据,与 `KeyStoreManager` 的威胁模型呼应。
- **缺**:`android:networkSecurityConfig` 在 `targetSdk = 28+` 上是可选的,但本项目涉及远程 SSH,建议显式拒绝明文流量(`cleartextTrafficPermitted="false"`),防止用户手滑把端口配到非 SSH 的 80/443。
- **缺**:`android:exported="true"` 合理(LAUNCHER 必需),但缺 `android:configChanges` 列表(横竖屏切换会重建 Activity,IO 协程会被 cancel 断开 SSH)。Sprint 2.5 应加 `android:configChanges="orientation|screenSize|keyboardHidden"` 保留 SSH 会话。

### 3.21 `app/build.gradle.kts` 🟡

- 依赖固定,OK。
- **缺**:`buildConfig = true` 已被部分项目用上(`PasswordAuthProvider` 的日志用 `BuildConfig.DEBUG` 守卫会更安全),目前没启用。开启后同时定义 `ENABLE_DEBUG_LOG`。
- **缺**:`vectorDrawables { useSupportLibrary = true }`——没用 vector 但加一道保护。
- **缺**:ProGuard / R8 规则在 release build 没禁用 minify;debug build 没配 `applicationIdSuffix = ".debug"`,会让 debug / release 互相覆盖安装(目前版本号都是 1)。
- **缺**:kotlin 编译器警告未开启 `-Xopt-in=...`。
- **建议**:`compose-bom` 升到 2024.12+ 获取性能优化。

## 4. 安全性(优先级降序)

| # | 风险 | 严重度 | 建议 |
|---|---|---|---|
| S1 | `PromiscuousVerifier` 默认接受任何主机指纹,无 known_hosts / TOFU | 🔴 高 | Sprint 2.5 加 `KnownHostsVerifier`,首次连接把主机指纹写入 `filesDir/known_hosts` |
| S2 | 私钥以**明文**存于 `filesDir/keys/*.pem`,只靠沙箱保护 | 🔴 高 | Sprint 2.5:用 Keystore AES key 加密 PEM 存盘 |
| S3 | `debug.log` 把 host/username 写入 app-private 但 adb 可读 | 🟡 中 | `BuildConfig.DEBUG` 守卫 + UI 开关 |
| S4 | `PasswordAuthProvider` 把 password SHA-256 截断 16 位写日志 | 🟡 中 | 仅在 `BuildConfig.DEBUG` 输出;生产彻底关 |
| S5 | `Auth.PasswordAuth` 持 `String`,无法原地清零 | 🟡 中 | 改 `CharArray` + 显式 `zeroOut()` |
| S6 | `appendText` 没用 `Charsets.UTF_8` 显式声明 | 🟢 低 | 加显式编码 |
| S7 | `AndroidManifest` 没禁用 cleartext traffic | 🟢 低 | 加 `usesCleartextTraffic="false"` |
| S8 | Activity 旋转会重建,断 SSH 会话 | 🟢 低 | `configChanges` 清单 |

## 5. 可维护性 / 扩展性

### 5.1 优点

- **包结构清晰**,按 `data/ssh/terminal/ui/theme` 分层,跨层调用方向正确。
- **测试替身齐备**:`FakeTransport` 写法独立,生产代码与测试代码不混。
- **README 详尽**,决策有理有据。

### 5.2 债

| 主题 | 问题 | 建议 |
|---|---|---|
| ViewModel 缺失 | `HanTermApp` 70+ 行 Composable 持有 `connectionState / endpoint / activeSession` 等多个 mutable state,既不可测又难复用 | 抽 `SshTermViewModel`,Composable 只渲染 |
| Composable 拆分 | `ConfigScreen` 382 行,单文件 4-5 个职责 | 拆 `CrashLogCard / PrivateKeyImporter / FingerprintSection` |
| View 复杂度 | `TerminalView` 315 行,内含 Termux 黑盒 hack + IME 路由 + Resize 监听 + Emulator 构造 | 拆 `TermuxViewBridge`(hack 集中)+ `ImeKeyRouter`(路由决策)+ `PtyResizeTracker` |
| Build 脚本 | 缺 R8/ProGuard 规则,debug/release 不分 applicationId | 加 `applicationIdSuffix`,启用 R8 |
| 错误模型 | `Result<SshSession>` 是 ok,但 `SshClient` 内部所有失败都吃掉 trace,UI 端只能拿 `t.message` | 引入 `sealed class SshError : Throwable()` 携带阶段(Auth/Kex/Channel) |
| Compose 错误处理 | ConfigScreen 用 `importError: String?` + `statusMessage: String?` 两个并行变量 | 统一 `data class UiMessage(val text: String, val severity: Severity)` |
| 国际化 | 全部 UI 字符串 hard-coded English | 加 `values-zh/strings.xml` |
| 日志 | 有两套:Tag-based `Log.i` + 文件 `appendDebugLog` + `crash.log` | 统一 `Timber`(测试成本低) |

## 7. 具体问题清单(按严重度)

### 🔴 高

## 9. 总评

**这是一个工程质量相当不错的 v0.1 → v0.2 项目**。架构层次清晰(数据/传输/终端/UI 严格分层),关键决策(双链路 IME 分离、AES-256-GCM、Transport 抽象、bcpkix 注册)都做了正确的取舍。文档密度高、测试覆盖实在,代码风格统一,甚至连 Gboard P0 竞态这种偏门 bug 都有专门的 fix 注释和测试钉死。

主要短板集中在三个方向:

1. **安全边界没收紧**:PromiscuousVerifier、明文私钥、未守卫的日志,在生产前必须收口。
2. **大文件 / 缺 ViewModel**:`TerminalView.kt` / `ConfigScreen.kt` / `HanTermApp.kt` 三处都是单文件 200+ 行,缺少 ViewModel 隔离,后续 Sprint 加功能(主机列表、SFTP)时会迅速失控。
3. **死代码 / 冗余结构**:`SshConfig` 两个 timeout 是文档而非配置;`try/catch/throw` 是空日志;`composingBuffer` 字段从未读——这些是 Sprint 1 修过 1-2 轮代码的常见残留,做一次清扫可显著降低维护成本。

整体而言,**进入 Sprint 3(主机列表)前的技术债处于"可接受但需要集中清理"的窗口期**。建议把上述 🔴 4 条和 🟡 第 5 条(私钥加密)放进 Sprint 2.5,作为真 SSH 接入后的安全收口;其余 🟡 放进 Sprint 3 随重构一并处理。
